Getting Started

Adafruit Playground is a wonderful and safe place to share your interests with Adafruit's vibrant community of makers and doers. Have a cool project you are working on? Have a bit of code that you think others will find useful? Want to show off your electronics workbench? You have come to the right place.

The goal of Adafruit Playground is to make it as simple as possible to share your work. On the Adafruit Playground users can create Notes. A note is a single-page space where you can document your topic using Adafruit's easy-to-use editor. Notes are like Guides on the Adafruit Learning System but guides are high-fidelity content curated and maintained by Adafuit. Notes are whatever you want them to be. Have fun and be kind.

    EWatch: an ESP32-S3 smartwatch you can program from blocks to C++

    EWatch is an ESP32-S3 dev board built into a watch. It has a 1.69" colour touchscreen, WiFi, Bluetooth, USB-C, an accelerometer and a haptic motor, all on a 34 x 28 mm board.

    It took me five years and four board revisions. The first version was an ESP32 and a tiny OLED on a breadboard. The power-management chip I chose for the PCB turned out to be unreliable, so this year I replaced it with a plain discrete charging circuit, and the board that finally worked went on the bench in May.

    You can program it at whatever level suits you:

    • drag-and-drop blocks on ewatch.cloud, flashed from Chrome over USB-C
    • C or C++ in the Arduino IDE or PlatformIO
    • MicroPython
    • or describe an app and let the AI assistant write it from drivers that already run on the watch

    The drivers are open source: github.com/Ewan-Wills/EWatch_Dev

    The full build story is here: youtu.be/X4DW4XNUbkc

    EWatch is on Kickstarter until 30 November, as a bare board, a self-assembly kit or a finished watch: kickstarter.com/projects/ewatch/ewatch

    I'd love to hear what Adafruit makers would build on it.

    From Rabbit Holes to Catacombs - Programming with AI

    Last year I wrote about my first foray into using AI to help develop a CircuitPython project for a GPS tracking tool: Going Down the Rabbit Hole of AI Coding - GPS Tracker.

    Since then, I have really embraced AI, and frankly, I write very little code myself anymore. The AI tools I use—typically GitHub Copilot, Copilot Chat, and Gemini—have become extremely capable with CircuitPython. I now do almost all of my development in VS Code, and my projects have become quite complex. In the past few months, I developed a Math Tutor and a Spelling Tutor with touchscreens, visual and verbal cues, scoring, and even competition modes.

    One of the core principles I stood by was that I need to understand what all the code is doing, and I feel I have enough experience with CircuitPython to keep up with what the AI is writing. Although it has become really good at structuring projects and suggesting the ways to do things, there are times when I have redirected the path the AI is taking. We make a good partnership - I am in complete control and it does most of the hard work.

    I recently saw this blog post and I was intrigued: Squachwatch for the "cheap-yellow-display" that Gamifies Detecting Things.

    I wasn’t interested in the gamification aspect, but I really liked the ability to track down all the different signals and devices around us. TalkingSasquach said he had done all the coding with AI, so I thought, “I can do that!”

    My first thought was to simply start with his code and remove the graphics and other game elements. But after looking at it, I quickly figured out that (a) I didn’t have a clue how the code worked, and (b) even if I did, stripping out the gamification would be a lot of work. As best I could tell, the code was essentially C++/Arduino.

    Side note: the idea of these “Cheap Yellow Displays” (CYDs) was also intriguing—a relatively inexpensive board with a lot of capability—so I ordered a couple to play around with.

    Many, many years ago, I did some rudimentary Arduino coding, so it wasn’t all Greek to me. Still, I knew I would need to invest a lot of time to become proficient enough to figure it all out. Then I quickly realized that AI could do the heavy lifting. After all, that was how the original project had been built. I pulled up Copilot and Gemini and started digging in. I learned about PlatformIO for VS Code, and since I already had a good working knowledge of VS Code, I fired it up, installed PlatformIO, and created my first project.

    My workflow was fairly straightforward. I used Copilot Chat to flesh out the general framework, and then I used GitHub Copilot in VS Code to write the code itself.

    This did break my core principle of understanding what all the code was doing, but I was amazed at how quickly the project came together. I soon realized that I was learning the code as I went. I found that I could follow what was being done, research and suggest the best libraries to use, and even tweak some of the UI code myself. Not only did I learn a lot about C++/Arduino development on a CYD, but I also learned how to use GitHub.

    In the end, I created something very different from what TalkingSasquach made, but it was my project, and it did the things I found useful. I created a Wi-Fi scanner, a complete BLE HID box that works with my phone, and timer functions similar to those in this project:  PyBadge Timer Box

    To top it all off, with the AI’s help, I built a modular framework that I can reuse for other project ideas without having to recreate all the underlying infrastructure.

    The developing project can be seen in this GitHub repository: CYD ESP32 WiFi-BLE-Timers Project.

    PHNTM One: a local AI desk companion built around Raspberry Pi 5

    I’m Jacob, the builder behind DeCampLabs. PHNTM One is my attempt to give everyday AI tasks a dedicated place on the desk, using a Raspberry Pi rather than depending on a cloud AI account.

    Owner-supplied image exported from ChatGPT, October 8, 2026. Screen details may differ from the current interface.

    What I built

    PHNTM One combines a Raspberry Pi 5 with 8 GB of memory, a 10.1-inch touchscreen, 256 GB microSD storage, a microphone, and a speaker. A compact wireless keyboard with a touchpad gives another way to interact with it.

    The idea is simple: capture a thought, ask about a document, or pick up a project without opening another cloud chat on the computer you are already working on.

    What it does

    • Local conversation: ask questions through text or voice. In Private mode, the model runs on the device.
    • Notes and ideas: type or dictate a thought, then ask for help organizing or developing it. The original stays separate from the AI draft, so you can review the suggestions.
    • Document questions: bring in PDF, text, and Markdown files and ask about them. Answers can include file and page references when supporting passages are found. References still need checking; AI can make mistakes.
    • Memory: explicitly save a useful detail, review it later, correct it, or ask the device to forget it.

    Local chat, memory, Notes, document questions, and voice can work without internet. Optional connected services have separate data paths; enabling cloud-assisted answers can send the question and selected context to that provider.

    Owner-supplied image exported from ChatGPT. This picture is not a performance measurement.

    The software and the trade-offs

    The device uses a Python application, Ollama for local model inference, Gemma 3 4B for the primary chat model, and local speech tools. The touchscreen is the main interface.

    Running a small model on a Raspberry Pi means accepting limits. Answers can take tens of seconds, longer Notes can take several minutes, and complex reasoning is stronger on larger cloud models. PHNTM One can also give a wrong answer. My focus is making the device useful while keeping those limits visible.

    Dragon Ball Radar: Devlog 2 - Prototype!

    This note was originally posted on extralongdivision.com

    Previously on Dragon Ball Z!

    In the last installment of this project I proved the concept with a Frankenstein dragon radar. I’ve actually got something that looks like the real deal now. Keep reading to learn about the development since the last update. In a future post I’ll detail the steps to reproduce the project.

    Electrical Design

    This section will be short. I had two action items since the last update and I only did one of them. Originally I wanted to make the board 0.8 mm1 instead of 1.6 mm. I decided to keep the PCB2 the same size since that’d lower the USB-C3 connector coming out the back of the enclosure (ominous noises). Also, even if the mounting pins weren’t soldered into place, the SMT4 pads would still adhere the connector to the board.

    The only electrical change I did was flip the battery connector polarity to match the ones I already have.

    Left: Version 1 battery connector with reversed polarity. Right: Version 1.1 battery connector with correct polarity.

    Mechanical Design

    Last post, I said I’d wait until new PCBs arrived before redesigning the enclosure. This cost me a couple days of messing with clearance just to mount the PCB. Ultimately I had to make the enclosure’s diameter bigger to correct this. Ironic, since that’s what I was trying to avoid during the original design phase described in the last post.

    The button actuator was another issue that I would’ve recognized sooner if I tried to assemble the radar.

    The actuator interferes with the user button such that it’s impossible to mount the PCB, even with the aforementioned clearance. Cutting a slot for the user button fixed the issue.

    Once I fit the PCB inside the enclosure, I couldn’t actually press the user button because the actuator interfered with the board.

    I fixed this by making the enclosure thicker and mounting the PCB in a deeper recess. But now the whole radar is too large to palm in one hand and press the button at the same time. I mentioned a wrist strap in the last post, but using one doesn’t actually help, or at least the ones I have don’t. Here’s me holding the radar as best as I can with a wrist strap on.

    A consequence of a thicker enclosure is the USB-C connector not being flush with the slot in the back. Said slot is larger to accommodate a more recessed connector.

    So it didn’t matter if the PCB was 0.8 mm or 1.6 mm. Again, I did this mechanical work after the boards arrived. Lesson learned.

    Lastly, the speaker nest was so tightly toleranced that removal caused disassembly.

    The speaker still works, thankfully. This mishap is actually a feature. A friction fit makes foam tape unnecessary to keep the speaker in place.

    Board Bring up

    Everything was plug and play with the updated PCB (version 1.1). I followed the same steps to put CircuitPython on the board and my code ran with no problem. This proves that the SD_MODE pull up resistor I changed to 1M ohms didn’t affect the sound quality from the first round of board bring up.

    I did see some differences between PCB version 1 and version 1.1 though. For V1, uploading new code only worked after a hard power reset. Pressing the reset button on the board didn’t help. This problem never happened with version 1.1. Also, the screen would glitch as if the signal timing was off whenever the heartbeat LED5 was on. Again, only for version 1 of the PCB. Not an issue for version 1.1. I haven’t reproduced this on camera yet.

    I’m also seeing streaks of discoloring on the display that I wasn’t seeing earlier. It doesn’t show up in photos well, but soft peach/orange vertical blotches overlay whatever’s being shown. It’s especially visible when the screen powers off. Not sure if this is a result of me driving the display incorrectly or some other problem. Either way, it’s negatively affecting the replica’s authenticity.

    Cosmetics

    If the cover photo didn’t give it away, I didn’t do any post processing on the enclosure. I don’t like the aesthetics, but I’m de-prioritizing looks over other projects/potentially adding more features.

    One practical cosmetic issue is screen brightness in direct sunlight. Here’s a side-by-side of the radar in the shade vs the sun.

    Left: dragon radar in shade. Right: dragon radar in direct sunlight

    The two images accurately represent the difference between shaded and direct light to the naked eye. For the latter, the display acts more like a mirror than a screen. I believe I’m driving the backlight at 100% brightness, but it is still not the most readable in the sun. Using the project for an outdoor scavenger hunt would be very difficult. I might have to source a different screen for future iterations.

    Next Steps

    I consider the first phase of this project done. The design files are available on the, still undocumented, repository. I promise to have a proper README there once I post the build tutorial here. Be on the lookout for some video content with the radar too.

    By mrogovp
    How TinyUSB uses MemBrowse to keep track of its memory footprint

    Many of TinyUSB's targets are small parts where the USB stack shares limited flash and RAM with the application. Every byte TinyUSB uses is a byte the user can't.

    That makes memory footprint a core concern for the project, and a hard one to keep track of. A change in a shared driver might add 80 bytes on one port and 400 on another, and nobody builds every board locally before opening a PR. Without tooling, growth can pile up unnoticed across hundreds of boards, and tracking down where it came from means digging through map files and rebuilding old commits.

    MemBrowse gives TinyUSB visibility into its memory footprint on every commit, so these changes are caught in the PR instead of weeks later. When something does grow, you can see exactly where the bytes went, which makes memory footprint investigation a breeze.

    What MemBrowse does

    MemBrowse runs as a step in your CI, on GitHub Actions or GitLab CI. After each build it reads the ELF, the linker script (for memory region limits) and optionally the map file (to attribute symbols to libraries). Each pull request gets a memory report comment showing how flash and RAM changed per target. Each target gets a history on the dashboard. Any change can be broken down by memory region, section and symbol, so you can see exactly what a commit added or removed and where it came from.

    How TinyUSB uses it

    TinyUSB's GitHub Actions workflow already builds every example for every board. MemBrowse runs on all of those builds, more than 2,100 of them, and posts a memory report on each PR.

    Example: TinyUSB PR #3574

    PR #3574 added board support for Nordic's new nRF54LM20 DK. The title only mentions the new board, but part of the change landed in code shared with other Nordic boards.

    The MemBrowse report on the PR showed the effect. Eight of the ten biggest changes were examples on the Adafruit CLUE, an existing board built on Nordic's older nRF52840. Each grew by about 1.4 KB of flash and 136 bytes of RAM, up to 21% on the board_test example.

    AIR PRO: a Pip-Boy style air quality monitor with Qualia S3 and SEN66

    I wanted an air quality monitor I can read from across the room, and I wanted it to look like something from a Fallout vault.

    AIR PRO reads CO2, particles (PM1.0 to PM10), VOC, NOx, temperature and humidity every 2 seconds. It turns all of that into one simple status: OPTIMAL, NORMAL, FAIR, CAUTION, WARNING or CRITICAL. It also tells you the main problem, for example "MAIN THREAT: CO2, VENTILATE ROOM".

    Everything runs on CircuitPython. No cloud, no app. WiFi is only used for a few seconds every hour to get the time.

    Full code, parts list and photos: github.com/ostgate/air-pro

    Parts

    • Adafruit Qualia ESP32-S3 for TTL RGB-666 Displays
    • 4" 720x720 square TFT display (RGB666)
    • Sensirion SEN66 (CO2, PM, VOC, NOx, temperature, humidity)

    • Adafruit I2C QT Rotary Encoder with seesaw
    • STEMMA QT / Qwiic cables
    • USB-C cable and a USB charger
    • A small wooden box (for now)

    All sensors and the encoder share one I2C bus through STEMMA QT cables. No soldering needed.

    Build

    The case is a small wooden box I had at home. The display sits in the door, with the Qualia board on its back. The SHT45 and SEN66 are mounted on the outside wall of the box, so they breathe room air and do not get heated by the board and the backlight. The rotary encoder shaft comes out of the top.

    Environment Overview: overall air status, CO2, temperature, humidity, dew point, PM2.5 and VOC.

    Meshtastic-compatible full stack (in 🦀) for CircuitPython

    If you want to get a Meshtastic-compatible library that works great in CircuitPython, of course there is no better place to start than the MeshFruit library!

    Yet, there is another library in town, that might be a have some extra steps to install it, but because it has been written in Rust, and for CircuitPython, it bridges the two things we like the most: an efficient and fast full stack library with the ease of use of CircuitPython.

    The way that it has been designed, you can connect to REPL and have the library already talking with the Meshtastic network, while you send messages or read your inbox using simple commands. But, if you power on the device and to manually take it to REPL, it will start running code.py acting as a Meshtastic client that you can connect with your phone via the official Meshtastic application, or you can interact with it over the network by using the official Meshtastic Python API.

    So, you can use the REPL for simplicity, learning how to use the library, quick serial console or web-workflow testing, use the default code.py that comes with the library to connect your phone with the same app everyone else is using, and of course you can call the library from your own CircuitPython code to let your project start talking with the amazing Meshstastic network.

    Compatible hardware

    Since me, the author of the library, only has a handful of hardware that is both capable of running CircuitPython and that has a LoRa radio, so far the list of hardware is a bit limited to a couple of new and shiny boards that Meshstastic enthusiasts are gravitating to, because of very useful features. With the library released, now I will work on adding support for Adafruit hardware, and later for popular Meshtastic hardware. So far, we got:

    • Muzi Works' Base Duo: nRF52840 with LR1121 radio. Cool features: 915MHz + 2.4GHz LoRa, BLE, integrated solar charger.
    • Meshnology W12: ESP32-S3R8 (same S3 we know and love, but with 8M of PSRAM!) with LR2021 radio. Cool features: 915MHz + 2.4GHz LoRa, FLRC! (more on this, below), WiFi, multi-net navigation device, OLED screen, comes with case, a very decent 915MHz antenna and battery.

    Note: This boards are not official CircuitPython supported hardware, yet. I'm working on it, but we found an external issue that Adafruit is trying to solve.

    Integrated devices

    • The latest generation of LoRa radios from Semtech: LR1121 and LR2021.
    • A navigation device (GNSS or "GPS")
    • An OLED screen

    How to install

    Any device

    • Use a CircuitPython build that has CIRCUITPY_ENABLE_MPY_NATIVE enabled. This might require a manual rebuild, but it's required for Rust support.
    • Copy the mpy files for the radio used in your board to the CIRCUITPY/lib on your board. Current support is for: LR1121 and LR2021
    • Copy the mpy files from the cpy-meshtastic library to the CIRCUITPY/lib on your board. Note: Since Rust is compiled, in a similar way to Turbo, you need to use the mpy files compiled for your board's arch.
    • Copy the code.py, repl.py, and settings.toml to the root of CIRCUITPY on your board. Edit settings.toml to configure the LoRa region, client short and long name, as well as any board specific features like WiFi connection, OLED, navigation device, and to enable how you want to connect to the Phone app.

    This is a short example of a settings.toml file:

    MESH_RADIO = "lr2021"

    By melastmohican
    epdsi on the Feather ThinkInk: From One Panel to Seven, One Socket

    Back in my earlier post, I wrote about bringing up a single JD79661 panel on this board with a driver built from scratch. That driver has since grown into epdsi, a published no_std, embedded-hal 1.0 Rust crate. I went back to the same ThinkInk Feather to see how far it reaches now.

    Answer: seven panels, five controller ICs, one 24-pin FPC socket, no wiring changes. Swap the panel, reflash, done. All seven verified working on the first attempt:

    Panel Controller Full refresh Partial/fast
    1.54" Tri-Color SSD1681 17,881 ms 17,881 ms (windowed, no saving)
    2.13" Mono SSD1680 3,893 ms 1,017 ms (differential)
    2.13" Quad-Color JD79661 20,041 ms —
    2.66" Tri-Color SSD1680 20,044 ms 16,176 ms (FastFull)
    3.52" Tri-Color UC8253 17,366 ms —
    3.7" Mono UC8253 2,615 ms 410 ms (FastPartial)
    4.26" Mono SSD1677 3,744 ms 500 ms

    Two things worth calling out. Colour panels have no fast path: narrowing the RAM window reduces what's redrawn, not what it costs, so a partial refresh on a Tri-Color panel takes exactly as long as a full one. Both UC8253 panels work fine here too, which is notable because an earlier bring-up on a different ESP32-C3 board logged them as non-functional. That module later turned out to be faulty hardware, and these clean first-try runs on the ThinkInk are the evidence the driver was never the problem.

    Full code, wiring notes, and measurement methodology: adafruit-feather-thinkink-discovery.

    Conclusion

    If you're on this board, epdsi is worth a look regardless of which panel you're holding. One driver, one socket.

    One thing I'd change on the hardware side, though. The 24-pin FPC connector is genuinely great: seven panels, zero wiring, swap and reflash. But this board ships with no SWD connector, so there's no RTT logging, the easy path everyone else on rp-rs gets by default.

    The workaround: route defmt over USB CDC instead, via defmt-bbq. epd.refresh() blocks for seconds at a time and USB needs polling every few milliseconds to stay alive, so that meant splitting the two cores. Core1 services USB and drains the defmt-bbq buffer; core0 runs the actual panel logic. It works, and every example in this repo uses it. But it's real plumbing I shouldn't have had to build just to see a log line mid-refresh.

    If there's a next revision of the ThinkInk Feather, please bring back SWD. RTT logging is the only sane way to see what's happening while a refresh is in flight, on a board that spends most of its time in long, blocking e-paper refreshes. Otherwise you're stuck inventing a second communication channel just to debug.

    Using an ESP32-S3 / S2 as a JTAG / SWD / CMSIS-DAP debug probe tool to debug anything (like a SAMD51 M4 Metro, Pico, or ESP)

    There's a good old (>3yrs) project called ESP-USB-Bridge. It turns any ESP32-S2 or ESP32-S3 into a fully functional debug probe tool, with JTAG or SWD, UART pass through, and UF2 flashing too.

    I'd been meaning to give it a try for ages, and this week I finally had the excuse to debug an uncooperative chip!

     Mainly my reasoning for wanting these is that each PicoProbe costs ~$12, and JLink even more, and I ideally want one debug probe per board in my Hardware Testing farm (bunch of boards in boxes, controlled via SBCs with USB PPPS hubs).

    Yes, you can use a Pico (~$6) as a pico probe, but that doesn't cover non SWD targets. Ideally I want to spend <$3 per target to add debugging, and cheap ESP32-S3 nano boards ($2 clones with bad aerial) seem ideal for that.

    The firmware I work on (Adafruit WipperSnapper) supports over 40boards, and 100 components/peripherals, so there's quite the combination to debug / support (too expensive for official probes). I also aspire to support as many CircuitPython boards as possible, and at 500 boards that's a tall order!
